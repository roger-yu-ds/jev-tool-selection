Right first pick (router mode, plain prompt)

Jev beats DeepSeek by 8 points on the same 600 messages (only Jev right 89, only DeepSeek right 44; McNemar p = 0.00012).

Two ways to fail

A wrong call is a tool that can't do the job: an order lookup for “cancel my order”. Squares are the LLMs with real tool calling; they ask a clarifying question on 24%–40% of messages.

first-pass labelsrevised labels: an FAQ search on a how-to question counts

Same picks. One defensible change to what counts as right, and the ranking flips: the LLMs read “how do I…?” literally; Jev hands off.

Every selector gains 8–26 points. Jev 82% and Sonnet 85% are level (p = 0.05); Jev makes 1.0% wrong calls, Sonnet 6.0%.

Measuring tool selection

  1. Real tool text, not tools written to fit your test set.
  2. Sets of acceptable answers, and “no tool” as a class.
  3. Report wrong calls next to accuracy. A hand-off and a bluff are not the same miss.
  4. Paired comparisons on the same messages (McNemar), not two accuracies.
  5. Write the policy down and put it in the prompt. Then you're measuring the model.
  6. Publish the labels. They decide the winner.

The score is a labelling decision. Make it on purpose.

A2 · Labels and scoring

  • A research pass mapped each intent to acceptable tools (a clean fit) and partial tools (a defensible first step). Four author overrides, each with a stated reason. 15 intents have no acceptable tool: only hand_off_to_human is right.
  • Revised labels (v2) also accept the store-FAQ search on the 15 gap intents, a hand-off on payment_issue, and the refund-policy FAQ on get_refund.
  • Outcomes: right · defensible · handed off (a tool could have done it) · asked (no tool call) · wrong · bluffed. Only right scores. Wrong + bluffed = the wrong-call rate.
  • Statistics: exact McNemar on paired right/wrong; 4,000-sample bootstrap for the difference; Wilson intervals for rates.
  • Prompts: identical text for the three LLMs; Jev gets the same question as a choice over names and descriptions. Temperature 0. Sonnet 5.5 can't disable reasoning, so it ran at low effort.

A3 · Router against native tool calling

The router condition pastes the tool JSON into the prompt and asks for a name; it's the like-for-like test against Jev. Native tool calling puts the tools in the API's tools parameter with tool_choice: auto, which is how an agent really works, and it may answer in text instead.

The found preamble
You are the tool router for an online store's customer-support assistant. The store runs on Shopify (storefront FAQ/policies, UCP cart/checkout/catalog/locations tools, customer-account tools), takes payments through Stripe, and uses Intercom as its helpdesk; staff also use GitHub and Notion. Input: `tools_json` (a JSON list of every available tool with name, description and input schema) and `message` (one customer message, often short, informal, typo-ridden, rude or oddly worded, sometimes using unusual synonyms such as 'reimbursement' for refund, 'bill' for invoice, 'consumer reclamation' for complaint). Pick the ONE tool that should be called first. Reply with ONLY the tool's exact name (e.g. shopify_storefront.search_shop_policies_and_faqs or hand_off_to_human), nothing else: no quotes, punctuation, JSON or explanation.

First work out the customer's underlying intent, translating odd wording into plain meaning. Messages come from intent categories such as check_cancellation_fee, check_refund_policy, set_up_shipping_address, edit_account, recover_password, payment_issue, track_order, get_invoice, complaint, etc. Then ask which listed tool can actually perform or answer that request.

Routing rules, with the domain knowledge learned so far:
1. shopify_storefront.search_shop_policies_and_faqs: use for questions about store policies, fees and charges, cancellation/return/refund/shipping/payment/terms rules, refund eligibility and timelines (e.g. 'under what circumstances can I request a reimbursement', 'how long do refunds take' -> check_refund_policy -> this tool), contact details, hours, and general how-it-works questions. Cancellation fees, delivery charges and return windows are policy questions even when the customer is angry or vague. Do NOT hand off just because the customer is upset or the wording is rough.
2. Payment problems: if the customer reports or asks how to report a problem with an online payment, a failed or wrong charge, or a payment that didn't go through (intent payment_issue, e.g. 'how do I inform of a problem with online payments?'), choose stripe.list_payment_intents, NOT the FAQ tool. Invoices/bills: 'where do I get the bill/invoice' or similar (intent get_invoice) -> stripe.list_invoices. Other Stripe uses: stripe.list_subscriptions / cancel_subscription for subscriptions, stripe.create_refund for refund execution, stripe.list_disputes for disputes. Distinguish: asking about refund POLICY or timing -> FAQ tool; reporting a concrete payment problem -> Stripe.
3. shopify_customer_account tools: the customer's own order status (get_order_status, get_most_recent_order_status), store credit balance, and return requests (request_return). shopify_ucp tools: browsing products, carts, checkouts, and store locations. Intercom tools are for helpdesk conversations/contacts/articles. GitHub and Notion tools are staff tooling and are almost never right for a customer message.
4. hand_off_to_human: choose ONLY when no tool can do what the customer asks. Typical cases: (a) account modification the tools do not offer: changing or setting up a delivery/shipping address, editing/updating account profile data or account details (e.g. 'update standard account'), recovering or resetting a password, PIN or login credentials ('retrieve the PIN of my user profile'); (b) complaints: where/how to lodge a complaint, claim, 'consumer reclamation', or file a grievance against the company (intent complaint) -> hand_off_to_human, since searching the FAQ or looking up an order does not do what the customer asked; (c) requests needing human judgment. Examples: 'where to submit a different delivery address' -> hand_off_to_human; 'where to lodge a consumer reclamation against ur company' -> hand_off_to_human.
5. Avoid both errors: do not use the FAQ tool for actions it cannot perform (address changes, credential recovery, account edits, filing complaints) or for concrete payment problems, and do not hand off when the FAQ/policy tool can answer (e.g. 'checking the cancellation charge', 'how long refunds take', 'when can I get a reimbursement' -> shopify_storefront.search_shop_policies_and_faqs). Key test: is the customer asking for information about a rule (FAQ) or asking to perform/submit/change something that no tool supports (hand off)?
6. Output the exact tool name string only.

A5 · Caveats and links

  • “No tool” means none in this catalogue. Shopify's customer-account server may expose more once a customer signs in; a store can add servers.
  • Bitext messages are template-generated and often vague; real tickets are longer and messier.
  • Jev sees names and descriptions; the LLMs also see schemas. That is how each is used, but it isn't identical information.
  • The routing policy lists example gap intents, which partly hands the models the labels. The GEPA appendix is the version that only saw a development split.
  • Costs are OpenRouter's billed prices with caching; Jev at US$0.042 per million input tokens.
