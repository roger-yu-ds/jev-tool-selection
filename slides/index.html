Correct

Wrong, but benign

“wanna get the bil from Chloe will uhelp me”

Jev hands off to a person: the customer waits, nothing breaks

Wrong, and harmful

“i havent signed up yet help me creatin a customer profile”

DeepSeek calls create_customer: it creates a customer in Stripe, the payments system, instead of a store account

Benign: handing off, asking a question, or reading the customer's own records. Harmful: changing something it shouldn't, or using a tool built for something else, such as GitHub's issue tracker or the helpdesk's internal records. In the final runs, harmful answers were rare: 3 in 2,400.

Results

Jev against Sonnet 5.5: 95% and 93% correct (only Jev right on 37 messages, only Sonnet 5.5 on 25; p = 0.16).

Jev only picks the tool, reading each tool's name and description (about 7,200 tokens). A second, small call to DeepSeek then fills in the chosen tool's arguments; Jev's row includes it (595 tokens, 1.1 s, $0.035 per 1,000). The LLMs pick and fill in one call, so they read every tool's full input schema: the same text for all three, which Claude's tokeniser counts as about 1.5 times as many tokens as DeepSeek's.

The tool list is the same on every call, so the providers cache it and bill repeat reads at 3–5% of the normal price; Jev bills every token at $0.042 per million. That is why cached DeepSeek costs about the same as Jev. Without a warm cache (quiet traffic, or tool lists that change per customer) the LLMs cost 25 to 500 times more.

Use both. Every message goes to Jev first. If Jev's confidence is 0.8 or higher, use its answer; otherwise send the message on to Sonnet and use Sonnet's answer. Only 27% of messages reach Sonnet.

Result: 96% correct (93% for Sonnet alone), 0.0% harmful, $2.73 per 1,000 messages instead of $9.07. The 0.8 cut-off was chosen on the development messages, before this data.

Customer wording cut Jev's unneeded hand-offs from 26% (development messages) to 9% of the messages a tool could handle (2% for Sonnet), but they are still 26 of its 28 mistakes. They come with low confidence: a median of 0.67, against 0.97 for its right hand-offs, which is what the 0.8 cut-off catches.

What we learned about measuring this

  1. Write down when to pass a customer to a person, and give it to every model.
    Three sentences of policy took Sonnet from 70% to 93% on the development messages.
  2. Describe each tool the way customers talk.
    “Download my bill”, not “This tool will fetch a list of Invoices from Stripe”. One extra line on six tools took Jev from 85% to 97%.
  3. Check the answer key against every failure.
    We found nine mistakes in ours. With the original key, Jev led Sonnet 74% to 63%; after the fixes and the policy, Sonnet led.
  4. Count harmless and harmful mistakes separately.
    Passing a customer to a person, or asking a question, is not the same as doing the wrong thing.
  5. Test on messages you didn't build with.
    Every number on the earlier slides comes from 600 fresh messages, drawn after all of the above was fixed.

The score is a design decision. Make it on purpose.

Appendix · A1 · Data and tools

  • Messages: from Bitext's customer-support dataset (26,872 rows; template-generated with deliberate typos; CDLA-Sharing-1.0). Bitext supplies only the customer messages and a label for the request type (27 types, such as “track order”); it knows nothing about tools. Which tools fit each request type is our answer key (A3). The main results use 600 fresh messages (22–23 per type), drawn after the study was designed, sharing no message and at most 58% of words with the 600 used during development.
  • Tools: 90 tools copied word for word from 7 official MCP servers. An MCP server is how a company lets an AI assistant use its product: it publishes a list of tools, each with a name, a description and the arguments it takes. We collected the lists three ways. Stripe (22 tools), GitHub (10) and Notion (24) publish their servers as software anyone can run, so we ran the official version and asked it for its list. Shopify's servers run on every Shopify store, so we asked a live public store (20 tools across three servers). Intercom's needs a login, so we copied its 14 tools from its documentation. The 91st tool, hand_off_to_human, is ours.
  • Stripe's hosted server has since replaced these 22 tools with generic read and write tools; we used the last version with one tool per task.

A2 · The setup

  • Every selector chooses from the same 91 tools: the 90 real ones plus hand_off_to_human, the one we added.
  • The LLMs work as real agents: the tools go in the API's tools setting, the way an AI app normally gives a model its tools, and the model decides by itself whether to call one or reply in text. Least-random setting (temperature 0), prompt caching on. Tool names are written server__tool because the API doesn't allow dots. Scored on the model's first move: its first tool call, or a question back to the customer.
  • Jev: one multiple-choice question whose 91 options are the tool names and descriptions; it returns a probability for every option.
  • Same routing policy for all four:
Routing policy:
1. The assistant serves the store's customers and may use the store's Shopify and Stripe tools to look up or act on that customer's orders, payments, refunds and invoices. If a tool can do what the customer wants, call it, even when the message is phrased as 'how do I ...?'.
2. Search the store's policies and FAQs only for questions about store policy: refunds, delivery, payment methods, fees, contact details.
3. If no tool can do what the customer wants (for example cancelling or editing a placed order, account changes, complaints, newsletters, reviews), pick hand_off_to_human. Don't search the FAQ instead.
  • Customer wording. Every tool comes with a short description written by the company that makes it, for example Stripe's list_invoices: “This tool will fetch a list of Invoices from Stripe.” We kept 84 of the 90 exactly as published. For six, we added one line at the end in the words customers use:
    • search_catalog: Customers say: 'I want to buy an article', 'help me order some items', 'I need to shop for a product'.
    • create_cart: Customers say: 'I want to buy this', 'add it to my cart'.
    • list_invoices: Customers say: 'where is my invoice', 'download my bill #123', 'check my bills'.
    • get_order_status: Customers say: 'status of order ORD-123', 'check bill/invoice #123', 'any news on my refund for order ...'.
    • get_most_recent_order_status: Customers say: 'where is my order', 'any news on my refund', 'I'm waiting for my reimbursement'.
    • request_return: Customers say: 'I want my money back', 'how do I get a refund', 'I want a compensation'.

A3 · The answer key

Per request type: the tools that are correct; benign answers (handing off where a tool existed, asking a question, or reading the customer's own records or the store's public information); and harmful ones (a change that wasn't asked for, or a tool built for something else: GitHub, Notion, the helpdesk's internal conversations and contacts, Stripe's developer docs). Handing off is correct on the 14 types no tool covers and benign elsewhere; asking a question back is correct where the tool needs details the message lacks. Every failure in the development runs was checked by hand; these changes came out of it:

  • check_invoice: For a shopper the bill is usually the order receipt; Stripe needs the customer before it can list their invoices.
  • contact_customer_service: Handing to a person is a defensible reading of 'contact customer service'. 'I want to call customer support': a person is customer service.
  • get_invoice: Same as check_invoice.
  • get_refund: Both refund tools need an order or payment ID first, so the lookup is the right first call. Starting a return needs the order and the items.
  • payment_issue: Someone reporting a payment problem should reach a person. Investigating needs to know what went wrong.
  • place_order: The task asks for the FIRST call: finding the product comes before creating a cart. Searching the catalogue needs to know what the customer wants to buy.
  • track_refund: get_order_status is listed as partial; its no-argument twin does the same job. Looking up the order (or the payment) shows whether the refund went through; the routing policy itself says to.
  • Every request type: Reading the customer's own records or the store's public information (including the FAQ) is at worst a wasted step: benign, never harmful.

A8 · Right tool, right arguments?

There is no answer key for argument values, so we checked what can be checked by rule, on every call to a correct tool other than a hand-off: the arguments match the tool's schema; every order number, ID or email comes from the message (none made up); an order number in the message is passed on; refund amounts are in cents. Free text (search queries, hand-off reasons) isn't scored. Jev's arguments come from its second, filling call.

A9 · Two changes to Jev's options

The LLMs can always reply with a question; Jev couldn't. We added a 92nd option, need_more_information, which an agent would turn into a question, and scored it exactly like an LLM's question. Separately, we added each tool's inputs (name, type, required or not) to the descriptions Jev reads, as the LLMs see the full input schemas. Ask-first rule: on refund, order and payment requests that give no order number or amount (like “I want my money back”), only a question, a hand-off or a lookup that needs nothing from the customer counts as correct, for every model.

Jev used the new option on 16% of messages, at low confidence (median 0.56). 41 were right (refunds, orders, payment problems); the rest replaced a correct invoice lookup, refund check or hand-off. A10 · Caveats

  • Bitext messages are template-generated and often vague; real tickets are longer and messier.
  • The customer wording and the routing policy were written while looking at the development messages; the fresh 600 test them on new messages from the same dataset, not on real traffic.
  • “No tool” means none in this catalogue: Shopify's customer-account server may expose more once a customer signs in, and a store can add servers.
  • The answer key is a judgement. It's published with a reason for every decision (src/toolpick/data.py), and the explorer re-scores everything if you change it.
  • Each message is scored on its own, as the first message of a chat from a signed-in customer with no order in view. With the conversation history, asking versus acting and the arguments would change (A8, A9). Argument values are checked by rule, not against an answer key. Sonnet 5.5 can't disable reasoning, so it ran at low effort. Costs are OpenRouter's billed prices; Jev at US$0.042 per million input tokens.
  • Jev reads names and descriptions; the LLMs also read schemas. That is how each is used.
